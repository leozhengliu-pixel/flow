## How the inventory was built

- `withColdMetadataRouteMux` asks the complete `ServeMux` which pattern wins before authentication. A nonempty pattern gets a COLD scope and the separate projection gate unless `scaleP21RouteTemperature` says `hot`. An unlisted registered pattern defaults to COLD. SW550 recomputes the table from all registrations, the SW286 flag-on call graph and the `server/` and `store/` inventory JSON. The table records the first reachable blocker. A second blocker can surface after the first is resolved. [Routing](../../api/cmd/server/cold_authorization.go), [SW550](../../api/cmd/server/route_temperature_guard_test.go), [Generated table](../../api/cmd/server/route_temperature.go), [Inventory](../../api/internal/store/scale_p21_inventory)
- `scaleP21ColdAuthorizationRoute` identifies 27 explicit facade bindings inside that larger set. These can lazily borrow a `BeginColdMetadataRead` facade from authorization and refresh it for the handler. The remaining patterns get default admission. A literal paged projection can borrow the COLD decode image. Other legacy authorization can use `ColdRequestView`, which retains a one-workspace image through request close. `coldCapable` also admits `WithColdWork` and work carrying a closed request scope. Legacy writers can take the COLD operation slot and refresh a facade against the installed generation under the shared writer lock. Accessor decodes use their own lanes. Scope entry, slot acquisition, and a full decode are separate observations. [Explicit bindings](../../api/cmd/server/cold_dispatch.go), [Authorization fallback](../../api/cmd/server/fallback_authorization.go), [Store scopes and views](../../api/internal/store/default_cold.go), [COLD writer](../../api/internal/store/cold_write.go)
- The appendix pairs each COLD pattern with its registration and first blocker. It includes the methodless MCP fallbacks (`ANY`), with POST on its own more-specific patterns. GET covers implicit HEAD under the mux. The 578 patterns contain 118 GET, 235 POST, 79 PATCH, 33 PUT, 111 DELETE and two methodless registrations. These are HTTP methods. Callback GETs can write, and some POSTs are previews or queries. Middleware redirects, unmatched requests and background-only jobs have no independent route row.
- The static SW550 listing test passed on this checkout with 889 patterns, 311 HOT and 578 COLD. SW530 sends GET and POST for each of three methodless patterns and skips the registered event stream. The two legacy account-deletion aliases in its skip list are absent on this branch. Its fast-mode count is therefore **580 COLD of 891 requests** by fixture pattern. The two methodless MCP patterns each contribute two requests to that count, even when the POST matches an explicit POST registration at runtime. The saved November 19 sweep in `~/.flow-local/live/lead-verify/t2b-testsserver88.log` measured 595 of 889 requests, 216 COLD slot acquisitions and 147 legacy accessor views on an older revision. Measure the migration delta with new before and after runs. SW530 compares status, normalized body and headers, rows, events, realtime and webhooks across legacy, warm bounded and SQL-reloaded bounded stores. Its fast-mode credentials and minimal bodies leave successful and denied branches to targeted tests. [SW530](../../api/cmd/server/scale_p21_sw530_route_sweep_test.go)

### Load acceptance on this machine

Run from the merged candidate checkout during the rig reservation. Build once. Use two MySQL-backed replicas with real Redis, the same 5,000-issue seed copied afresh by each `start`, the default workload mix and the local fake model. Keep peer sync and the catalog worker off in both arms for a one-flag comparison, use the same read rotation and memory limits, and reset the private Redis database between runs. The rig's reported `overall.errorRate` is `(5xx + network errors + timeouts) / requests`. Review new or increased 4xx by operation before accepting the result. Record p99, projection-gate and freshness causes, RSS and realtime stream failures alongside it.

Find the highest stable flag-off step with two 180-second runs at each of 10, 20, 30, 50 and 70 VUs. A step fails if either repeat exceeds 0.5% errors or 2,000 ms p95. Stop climbing at the first failed step. If 10 fails, repeat the procedure at 5 VUs and record that result separately. If 70 passes, report the highest tested step and reserve higher steps if the ceiling is needed. At that same stable concurrency require both flag-on repeats to meet the same limits. Proposed thresholds for a clear improvement are at least 20% lower p95 and 10% more successful HTTP responses per second versus each matched flag-off repeat. `overall.ok` counts 2xx and 3xx. Keep the 100-VU pair as a secondary stress check even when the stable point is lower. Preserve all reports and the candidate commit for review.
