# Loops API contract (backend, 2026-09-29)

Backend contract for the Linear-parity Loops UI. All endpoints are workspace scoped (`X-Workspace-Key` as usual).
Fields marked *(new)* were added in this round; everything else already existed. Stored loops created before this
round are returned in the new shape (see "Backward compatibility").

## Loop

```ts
interface Loop {
  id: string
  name: string                 // may be "" while a draft
  description: string          // (new) one-line summary, generated by the model on publish / instruction change
  status: "draft" | "published" // (new) old loops = "published"
  templateId?: string          // (new) template the draft started from
  sourcePrompt?: string        // (new) "Ask Linear to build…" request the draft started from
  icon?: string
  color?: string
  level: "workspace" | "team"
  teamId?: string              // (new) owning team when level = "team"
  triggerType: "schedule" | "issue" | "project" | "initiative" | "release" | "team" | "cycle"
  triggerConfig: TriggerConfig // always normalized to the new shapes below
  instructions: string
  connectorIds: string[]
  // Permissions
  teamAccess: "allPublic" | "selected"   // "selected" uses triggerConfig.teamIds
  allowChangesOutsideTrigger: boolean
  allowExternalSync: boolean   // "Allow changes to externally synced issues and comments" (input alias: allowExternalSyncChanges)
  webSearch: boolean           // (new) offers web_search/fetch_url to runs when a provider is configured (see "Web search" below)
  codeAccess: "disabled" | "read" | "readWrite" // (new) old loops = "read" (still gated by workspace Code access for automations)
  enabled: boolean             // drafts are always enabled=false
  ownerId?: string
  trustedSourceKeys?: string[]
  creator: User
  lastRunAt?: string
  nextRunAt?: string           // schedule loops only
  runCount30d: number          // (new) computed: runs started in the last 30 days (from retained history, max 50 per loop)
  createdAt: string
  updatedAt: string
  publishedAt?: string         // (new)
}
```

### TriggerConfig

Schedule (`triggerType: "schedule"`):

```ts
{ startDate: "2026-09-29", interval: 1, unit: "hour" | "day" | "week" | "month", time: "07:00",
  weekdays?: ("sun"|"mon"|"tue"|"wed"|"thu"|"fri"|"sat")[], timezone?: "Europe/Berlin" }
```

- `hour`: every `interval` hours starting at `startDate` + `time`.
- `week` + `weekdays`: runs at `time` on each listed weekday of every `interval`-th week (weeks counted from the week
  of `startDate`). `day` + `weekdays` runs only on those weekdays. Without `weekdays`, weekly runs repeat the start
  weekday.
- Legacy key `starting` is still accepted and is returned as `startDate`.

Issue (`triggerType: "issue"`):

```ts
{
  event: "created" | "updated" | "triage" | "status" | "priority" | "assignee" | "agent" | "project" | "team"
       | "labels" | "comment" | "customerRequest",
  value?: string | null,       // what the property was set to; "any"/absent = any value; null = "none" (No assignee…)
  teamIds?: string[],          // "in [Select teams…]"; empty = all teams the loop may access
  filters?: { field: "status"|"priority"|"assignee"|"label"|"project"|"team"|"creator", operator: "is"|"isNot",
              value: string | null }[]   // null = No assignee / No project
}
```

Event semantics (all fire only for issues in scope; issues created by a loop run never trigger loops):

| event | fires when | `value` |
|---|---|---|
| created | an issue is created | – |
| updated | any property of an issue changes ("Property updated") | – |
| triage | the issue enters its team's triage queue: created into triage or moved into it (team triage enabled, state type `backlog`, `triagedAt` empty) | – |
| status | the state actually changed | state id, state name, state type (`backlog`,`unstarted`,`started`,`completed`,`canceled`), `"triage"`, `"duplicate"`, or `"any"` |
| priority | priority changed | `0`–`4` (as string), label ("High"), or `"any"` |
| assignee | assignee changed | user id, `null` (unassigned) or `"any"` |
| agent | delegate (agent) changed | user id, `null` or `"any"` |
| project | project changed | project id, `null` or `"any"` |
| team | issue moved to another team | team id or `"any"` |
| labels | a label was added | label id or name, or `"any"` |
| comment | a new comment was posted | – |
| customerRequest | a customer request was linked to the issue (created with the issue or moved onto it) | – |

`filters` are evaluated on the issue after the change. Filter values: status = state id/name/type or `triage`;
priority = number or label; assignee/creator = user id (`null` = none); label = label id or name; project = project
id (`null` = none); team = team id.

Project / Initiative / Release / Team / Cycle:

```ts
{ event: "created" | "updated" | "status" | "update" | "started" | "completed", teamIds?: string[] }
```

| type | events supported |
|---|---|
| project | created, updated, status (project status changed), update (new project update posted) |
| initiative | created, updated, status, update (new initiative update posted) |
| release | created, updated, status (status or stage changed) |
| team | created, updated |
| cycle | created, updated, started, completed |

Legacy configs (`{action: "created" | "created or updated", filter, filterField, filterOperator, filterValue}`) are
mapped on read: `action: "created"` → `event: "created"`, otherwise `event: "updated"`; the single filter becomes
`filters[0]`.

## Loop run

```ts
interface LoopRun {
  id: string
  loopId: string
  status: "running" | "completed" | "failed"
  trigger: "manual" | "schedule" | "event"
  triggerLabel: string         // (new) "Manual run" | "Scheduled run" | "Triggered by DEV-14 status → Triage" …
  eventType?: string           // domain event, e.g. "issue.updated"
  entityType?: "issue" | "project" | "initiative" | "release" | "team" | "cycle"
  entityId?: string
  entityIdentifier?: string    // DEV-14 for issues, name for other entities
  actorId?: string
  output?: string              // final summary; streamed in while running
  steps?: { order: number, title: string, message?: string, at: string }[]   // (new) report_progress steps
  toolCalls?: {
    order: number              // (new) shared ordering with steps
    id?: string                // (new)
    name: string               // tool name, e.g. "save_issue"
    label: string              // (new) short human label, e.g. "Updated issue", "Searched issues"
    args?: string              // (new) short argument summary, e.g. "DEV-14 · priority High"
    status: "running" | "completed" | "error" | "blocked"
    error?: string
    startedAt?: string         // (new)
    finishedAt?: string        // (new)
  }[]
  error?: string
  startedAt: string
  finishedAt?: string
}
```

Runs are persisted incrementally while running (at most every ~750 ms, plus on every step/tool start/finish), so
polling `GET /api/loops/{id}/runs/{runId}` shows live progress. Loop runs may take up to 24 tool turns; if that
limit is reached the model gets one final no-tool turn to write the summary instead of failing.

## Endpoints

| Method & path | Body | Response |
|---|---|---|
| `GET /api/loops` | – | `Loop[]` (drafts included; filter by `status`) |
| `GET /api/loops/{id}` | – | `Loop` |
| `POST /api/loops` | `{name?, level: "workspace"\|"team", teamId?, templateId?, prompt?, …any Loop input field}` | `201 Loop` — a **draft** (`status:"draft"`, `enabled:false`). With `templateId` the name/icon/color/description/trigger/instructions come from the template. Team templates (`requiresTeam`) need `level:"team"` + `teamId` (400 "Triage loops must belong to a team"). Passing `status:"published"` creates a published loop directly (legacy/API use). |
| `PATCH /api/loops/{id}` | any Loop input field; publish with `{status:"published", enabled:true}` (`enabled` defaults to true when publishing) | `Loop`. Publishing requires a name and instructions (400 otherwise). A published loop cannot go back to draft. Drafts cannot be enabled (400). Errors come back as `{error: "invalid input: …"}`. |
| `DELETE /api/loops/{id}` | – | 204 |
| `POST /api/loops/{id}/duplicate` | – | `201 Loop` — a draft copy named "<name> (copy)" |
| `GET /api/loop-templates` | – | `LoopTemplate[]` |
| `GET /api/loops/{id}/runs` | – | `LoopRun[]` newest first |
| `GET /api/loops/{id}/runs/{runId}` | – | `LoopRun` |
| `POST /api/loops/{id}/runs` | `{entityType?, entityId?}` | `202 LoopRun`. Required for non-schedule loops (`entityType` = loop trigger type, `entityId` = id or identifier like `DEV-14`); the entity must be in the loop's team scope (400 otherwise). Drafts cannot run (409). |

Loop input fields (POST/PATCH): `name, description, status, icon, color, level, teamId, triggerType, triggerConfig,
instructions, connectorIds, teamAccess, allowChangesOutsideTrigger, allowExternalSync (alias
allowExternalSyncChanges), webSearch, codeAccess, enabled, ownerId, trustedSourceKeys`.

## Agent (loop builder)

- Agent session create (`POST /api/agent/sessions[/stream]`) and follow-up messages accept `loopIds: string[]`
  (stored on the session as `loopIds`). When a loop in `loopIds` is a draft, the agent gets a loop-builder system
  prompt section and a `ask_question` tool.
- First message the web sends: template → `Set up this loop from the <template name> template`; prompt → the user's
  request text.
- Template drafts: the agent asks 1–3 questions, each rendered as an `elicitation` message part
  (`elicitation.requested` / `elicitation.resolved` stream events, same as connector elicitations):
  `connectorName: "Flow Agent"`, `mode: "form"`, `message` = the question, `schema =
  {type:"object", properties:{answer:{type:"string", title:<question>, enum:[2–3 short options]}}, required:["answer"]}`.
  Answer via the existing `POST /api/agent/sessions/{id}/elicitations/{elicitationId}` with
  `{action:"accept", content:{answer:"<option>"}}` (or `decline` to skip). After each answer the agent calls
  `save_loop`; after the last one it publishes and enables the loop. Once answered, the elicitation part is re-sent
  (`elicitation.resolved`) with `text` = the chosen answer and `toolCall` = the `ask_question` call (its `result` is
  `{"answer": "..."}`); render it as the answered chip question, not as a tool row. While the model streams the call a
  transient `toolCall` part named `ask_question` may appear (`tool.started`); hide tool rows named `ask_question`
  (the stored message never contains one).
- Prompt drafts: the agent fills name/trigger/instructions via `save_loop` and does not publish ("It remains a draft
  for your review; I didn't publish, enable, or run it").
- `save_loop` calls on a loop in the session's `loopIds` are auto-approved (no approval card).
- Tool rows: `toolCall.title` *(new, on AgentToolCall)* is `"Updated workflow definition draft"` for draft edits and
  `"Created automation"` when the call published the loop. `toolCall.result` holds the loop card data:
  `{id, name, description, status, enabled, trigger, triggerConfig, level, teamId, teamName, runCount30d, url, published}`.

## MCP `save_loop` additions

`status: "draft"|"published"` (or `publish: true`), `description`, `event`, `value`, `filters`, `teams`,
`weekdays`, `startDate`, `unit: "hour"`, `webSearch`, `codeAccess`, `allowExternalSync`, `templateId`.
Creating without `id` makes a draft unless `publish: true`.

## Backward compatibility

- Missing `status` → `published`; missing `codeAccess` → `read`; legacy trigger configs mapped as above.
- `POST /api/issues/{id}/loop-runs` (issue "Run loop on…") is unchanged.

# Round 2 additions (2026-09-29, backend)

Everything below is additive; existing fields and endpoints keep their shape.

## Loop — new fields

```ts
interface Loop {
  // …all fields above…
  instructionsData?: object     // (new) ProseMirror/Tiptap JSON of the instructions (same schema as issue descriptionData).
                                //  Stored as given. `instructions` (markdown) stays authoritative for the model; when a
                                //  request sends only `instructionsData`, `instructions` is derived from it as plain text.
  attachments?: LoopAttachment[] // (new) files attached to the "Ask Flow to build the loop" prompt (POST /api/loops attachmentIds)
  version?: number              // (new) current published version number (absent for drafts)
  versionId?: string            // (new) id of the current published version
}
```

Loop input fields (POST/PATCH) gain `instructionsData` (object or `null` to clear). `POST /api/loops` also accepts
`attachmentIds: string[]` (see Attachments).

At run time the prompt gets the markdown `instructions` plus a "Referenced in the instructions" list built from the
mention nodes in `instructionsData` (`{type:"mention", attrs:{id, label, mentionType:"user"|"issue"|"project"|"document"|…}}`),
e.g. `- Issue DEV-4 "Import your data" (id issue_123)`, `- Project "Onboarding" (id project_9)`,
`- User Ada Lovelace (id user_2)`, `- Document "Runbook" (id doc_4)`. Unknown/deleted entities fall back to the node's
`label`/`title`.

## Published versions ("Show published versions")

A version is recorded every time a loop is published (draft → published, or created with `status:"published"`), every
time a **published** loop's definition changes (name, trigger type/config, instructions/instructionsData, connectors,
permissions = teamAccess/allowChangesOutsideTrigger/allowExternalSync/webSearch/codeAccess, level/team), and on
restore. Pure enable/disable, owner, icon/color or generated-description changes do not create versions. The last 50
versions per loop are kept (version numbers keep counting up). Deleting a loop deletes its versions.

```ts
interface LoopVersion {
  id: string                  // "<loopId>_v<version>"
  loopId: string
  version: number             // 1..n
  publishedAt: string
  publishedBy: User           // who published/changed it
  changeSummary: string[]     // "published" (v1) | "restored" | "name" | "trigger" | "instructions" | "connectors"
                              // | "teamAccess" | "allowChangesOutsideTrigger" | "allowExternalSync" | "webSearch"
                              // | "codeAccess" | "level"   (level also covers teamId)
  restoredFromVersion?: number // set when the version was created by a restore
  current: boolean            // true for the newest version
  definition: {
    name: string; description: string; icon?: string; color?: string
    level: "workspace" | "team"; teamId?: string
    triggerType: Loop["triggerType"]; triggerConfig: TriggerConfig
    instructions: string; instructionsData?: object
    connectorIds: string[]
    teamAccess: "allPublic" | "selected"; allowChangesOutsideTrigger: boolean; allowExternalSync: boolean
    webSearch: boolean; codeAccess: "disabled" | "read" | "readWrite"
  }
}
```

| Method & path | Body | Response |
|---|---|---|
| `GET /api/loops/{id}/versions` | – | `LoopVersion[]` newest first. Drafts → `[]`. Published loops created before versions existed get a synthesized v1 (current definition, `publishedAt` = loop.publishedAt/createdAt, `publishedBy` = creator). |
| `GET /api/loops/{id}/versions/{versionId}` | – | `LoopVersion` (404 if unknown) |
| `POST /api/loops/{id}/versions/{versionId}/restore` | – | `200 Loop` — the snapshot's definition is applied to the loop and recorded as a **new** version (`changeSummary` starts with `"restored"`, `restoredFromVersion` = the restored number). `enabled`, owner and run history are unchanged. Draft loops → 409. |

Runs record the version they ran:

```ts
interface LoopRun {
  // …
  versionId?: string   // (new) LoopVersion.id current when the run started
  version?: number     // (new) its number — "Ran version 3"
}
```

## Run feedback (👍 / 👎)

`POST /api/loops/{id}/runs/{runId}/feedback` body `{rating: "up" | "down" | null, comment?: string}` → `200 LoopRun`.
One entry per user (a new rating replaces the viewer's previous one); `rating: null` removes the viewer's feedback.
`comment` is trimmed, max 2000 characters, kept only with a rating. Works on running and finished runs.

`LoopRun` gains (on list, get and the feedback response):

```ts
{
  feedback?: { userId: string, rating: "up" | "down", comment?: string, at: string }[]
  viewerRating: "up" | "down" | null     // always present
  viewerComment?: string
  feedbackCounts: { up: number, down: number }  // always present
}
```

## Web search

Server-wide provider, configured by env (no scraping of search engines):

| Env | Meaning |
|---|---|
| `FLOW_WEB_SEARCH_PROVIDER` | `tavily` \| `brave` \| `searxng` \| empty (disabled, default) |
| `FLOW_WEB_SEARCH_API_KEY` (or `_FILE`) | required for `tavily` and `brave` |
| `FLOW_WEB_SEARCH_URL` | required for `searxng` (base URL, JSON format must be enabled on the instance); optional override of the API base for `tavily`/`brave` |

Tools (provider-agnostic, read-only, never need approval):

- `web_search {query: string, maxResults?: number (1-10, default 5)}` → `{results: [{title, url, snippet}]}`
- `fetch_url {url: string}` → `{url, finalUrl, title, contentType, text, truncated}`. http(s) only; private, loopback,
  link-local, CGNAT, multicast and unspecified addresses are refused (checked when connecting, so DNS rebinding is
  blocked too); at most 3 redirects, each re-checked; 10 s timeout; body read up to 2 MB; HTML is reduced to readable
  text (scripts/styles/nav dropped); `text` capped at 60 000 characters (`truncated: true`).

Who gets them:

- Loop runs with `webSearch: true` when a provider is configured. The loop system prompt tells the model to cite the
  URLs it used. Run tool rows: `web_search` → label `"Searched the web"`, args = query; `fetch_url` → `"Read web page"`,
  args = url.
- Loop runs with `webSearch: true` and **no** provider: the tools are not offered, the prompt says web search is
  unavailable, and the run gets a notice: `LoopRun.notices?: string[]` (new) containing
  `"Web search is enabled for this loop, but no web search provider is configured on this server."` — show it on the run
  page.
- Flow Agent chat (all surfaces) when the workspace setting `agentWebSearch` is true and a provider is configured. Chat
  tool rows are ordinary `toolCall` parts named `web_search` / `fetch_url`.

## Loops settings (workspace level) — trusted sources, web search availability

Linear keeps trusted sources out of the loop editor; the editor should link to Loops settings instead.

| Method & path | Who | Body | Response |
|---|---|---|---|
| `GET /api/loop-config` | anyone who can use Loops | – | `LoopConfig` |
| `GET /api/workspace/loop-settings` | admins | – | `LoopConfig` |
| `PATCH /api/workspace/loop-settings` | admins | `{externalLoopTriggers?, trustedSourcesMode?, trustedSourcesAllowlist?, agentWebSearch?}` | `LoopConfig` (400 on invalid mode/keys) |

```ts
interface LoopConfig {
  webSearchAvailable: boolean            // a provider is configured on this server
  webSearchProvider: "tavily" | "brave" | "searxng" | ""
  agentWebSearch: boolean                // workspace setting: web search in Flow Agent chat
  codeAccessAvailable: boolean           // workspace allows automations to access code (Code access setting)
  externalLoopTriggers: boolean          // "Allow external sources to trigger loops"
  trustedSourcesMode: "none" | "allowlist"
  trustedSourcesAllowlist: string[]      // keys, see below
  trustedSourceOptions: { key: string, label: string, kind: "integration" | "appUser" }[]
}
```

Trusted source keys: `integration:<source>` (e.g. `integration:slack`, `integration:email`, `integration:intercom`) and
`appUser:<userId>`. `trustedSourceOptions` lists connected integrations, email intake and app users. The same fields
are still accepted by `PATCH /api/workspace/preferences` (which now also rejects an invalid `trustedSourcesMode`).
Per-loop `trustedSourceKeys` keep working but should no longer be edited in the loop editor.

## Attachments for "Ask Flow to build the loop"

1. Upload each file: `POST /api/loops/attachments` (multipart form, field `file`, max 20 MB, workspace upload policy
   applies) → `201 LoopAttachment`.
2. Create the draft: `POST /api/loops` with `{prompt, attachmentIds: [...], level, teamId?}`. Only the caller's own,
   not-yet-used uploads are accepted (400 `unknown attachment` otherwise); they move onto `loop.attachments`.
   Unused uploads are removed after 24 h.
3. Start the builder chat as before (`loopIds: [draftId]`, first message = the prompt text). The server adds the draft's
   attachments to the first user message sent to the model: images (png/jpeg/gif/webp ≤ 5 MB, max 4) as image inputs
   (all three agent protocols), text-like files (text/*, md, csv, json, xml, yaml… ≤ 100 KB each, 200 KB total) as
   extracted text, anything else as a one-line "Attached file name (type, size)". The web must **not** inline the files
   into the message text itself.

```ts
interface LoopAttachment {
  id: string
  name: string
  contentType: string
  size: number
  url: string          // "/uploads/…" — served to workspace members
  createdAt: string
}
```
